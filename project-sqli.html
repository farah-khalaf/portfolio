Applied Security · ASP.NET Core

SQL Injection Demo

A small ASP.NET Core web application, built deliberately with an insecure data layer, to demonstrate exactly how a SQL injection vulnerability comes to exist and how it would be exploited against a login flow.

C# / ASP.NET Core Entity Framework Core SQL Server

The vulnerable data model

The project's User entity stores credentials as plain, unhashed strings — the first ingredient of a vulnerable authentication flow, since it means any successful injection exposes real passwords, not hashes.

public class User
{
    public int Id { get; set; }
    public string Username { get; set; }
    public string Password { get; set; }  // stored in plain text — no hashing
}

Where the injection lives

Once credentials are stored as plain strings, the risk compounds if a login query is built by concatenating user input directly into SQL rather than using parameters — for example, checking a username and password with a raw, string-built query instead of EF Core's parameterized LINQ methods. An attacker submitting something like ' OR '1'='1 as the password turns the query's logic against itself, since the injected text is interpreted as SQL rather than as data.

The fix: use EF Core's parameterized queries (or a stored procedure with typed parameters) instead of string concatenation, and hash passwords with a salted algorithm like bcrypt or PBKDF2 so that even a successful breach doesn't expose usable credentials.

Why build the vulnerable version at all

Understanding an attack from the inside — writing the exact code that creates the weakness — makes it far easier to recognize the same pattern later in real applications, and to explain to a team why "it's just a login form" is rarely a safe assumption.
